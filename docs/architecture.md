# 系统架构设计

## 产品定位

自媒体内容工厂：用户输入一个选题，策划 Agent 拆解任务，4 个内容 Agent 并行产出公众号长文、短视频脚本、小红书文案和配图，全程在看板上可见、可中断、可重跑。

## Agent 角色与协作模式

采用「策划 + 并行执行」的轻量层级模式（简化版 Supervisor）：

```
选题 → 策划Agent → [长文Agent, 脚本Agent, 小红书Agent, 配图Agent]
```

- **策划 Agent（Planner）**：拿到选题后，为每个平台生成专属写作提纲（角度、结构、侧重点）。它的输出是 4 个内容 Agent 的输入。
- **长文 Agent**：根据提纲生成公众号风格长文（2000字+）。
- **脚本 Agent**：根据提纲生成短视频脚本（分镜+台词）。
- **小红书 Agent**：根据提纲生成小红书图文（标题+正文+标签）。
- **配图 Agent**：分两步，先把提纲里的配图描述扩写成高质量出图提示词（流式可见），再把提示词交给 Seedream 生成真实图片。

4 个内容 Agent 之间无依赖，并行执行；但它们都依赖策划 Agent 的输出，构成真实的上下游协同关系。

下游三个文本 Agent 的入参是「策划提纲 + 运行时选定的风格模板」：提纲决定写什么（角度、结构、侧重点），风格模板决定怎么写（文风、格式、排版、标签），两者互相独立、可自由组合。配图 Agent 只使用提纲里的配图描述，不参与风格模板。

### 失败处理规则

1. **策划节点失败（含自动重试后的失败）**：整个流水线阻塞，后置 4 个节点全部不启动。前端看板提示「策划提纲生成失败，无法继续生成内容」。
2. **后置 4 个节点互相独立**：任意一个失败，另外 3 个继续跑完。
3. **单节点重跑**：支持单独重跑任意一个后置节点。重跑时复用已经生成好的策划提纲，不需要重新跑策划 Agent。

### 策划 Agent 提纲 JSON 强制校验

后置 4 个节点强依赖策划 Agent 输出的**标准 JSON 提纲**。大模型经常额外输出解释文字、前言后记、markdown 代码块标记（```json），导致 JSON 解析失败、下游节点无法启动。因此对策划节点做**唯一**的强校验，其他 Agent 不做此校验。

**1. System Prompt 强制约束（`lib/agents/planner.ts`）**

策划 Agent 的 System Prompt 明确要求：

- 只输出纯 JSON，不输出任何解释、前言、后记
- 禁止使用 markdown 代码块标记（```json / ```）
- 禁止在 JSON 前后添加任何文字
- 输出必须能被 `JSON.parse` 直接解析

约定的提纲 JSON 结构（本轮**不校验**字段与结构，先保留作为后续迭代开发依据）：

```json
{
  "topic": "选题",
  "outline": {
    "longForm": { "angle": "切入角度", "structure": ["段落要点1", "段落要点2"] },
    "script": { "angle": "切入角度", "shots": ["分镜1", "分镜2"] },
    "xhs": { "angle": "切入角度", "headline": "标题", "tags": ["标签1"] },
    "image": { "angle": "切入角度", "prompts": ["配图描述词1"] }
  }
}
```

**2. 编排引擎解析校验（`lib/orchestrator.ts`）**

拿到策划 Agent 的输出后：

- 先去掉首尾空白，再执行 `JSON.parse`
- **本轮只做 JSON 语法解析校验**：`JSON.parse` 成功即放行，不校验字段是否齐全、结构是否正确
- 语法合法 → 策划节点标记 `completed`，启动 4 个并行节点
- 语法非法（`JSON.parse` 抛错）→ 进入自动重试流程
- 字段与结构完整性校验放到后续迭代补充

**3. 自动重试机制**

```
策划 Agent 输出
      │
      ▼
  JSON.parse 校验
      │
  成功 ├──► 策划节点 completed ──► 并行启动 4 个后置节点
      │
  失败 └──► 自动重试 1 次（重新调用策划 Agent）
                 │
             成功 ├──► 策划节点 completed ──► 并行启动 4 个后置节点
                 │
             失败 └──► 策划节点 failed ──► 阻断下游 4 个节点
```

- 最多自动重试 **1 次**，重试依然失败才判定策划节点 `failed`
- 判定失败后，后置 4 个节点保持 `pending`，一律不启动

**4. SSE 事件协议**

所有事件都按 `id: <自增序号>` + `event: <名称>` + `data: <JSON>` 推送。完整清单：

| 事件 | 时机 | data 结构 |
|---|---|---|
| `snapshot` | 连接建立时（含断线重连）先推一次全量 | 见下方「全量快照」 |
| `node:start` | 节点开始（自动重试会再发一次，attempt 递增） | `{ nodeId, name, model, attempt }` |
| `node:token` | 收到一个 token | `{ nodeId, text }` |
| `node:image` | 配图出图成功 | `{ nodeId, url, prompt }` |
| `node:done` | 节点完成 | `{ nodeId }` |
| `node:error` | 节点失败 | `{ nodeId, message }` |
| `node:cancelled` | 节点被中断 | `{ nodeId }` |
| `run:done` | 流水线结束（含中断收尾） | `{ summary, report }` |
| `run:failed` | 策划失败导致流水线终止 | `{ message, summary, report }` |

另外每 15 秒推送一行 SSE 注释 `: ping <时间戳>` 做保活，防止反向代理按空闲时间切断长连接；注释行不产生业务事件。

**全量快照**

`snapshot` 是唯一能让前端收敛状态的事件，结构：

```ts
{
  runId: string;
  topic: string;
  variant: "analysis" | "story" | "beginner" | null;
  styles: { longform?: StyleSnapshot; script?: StyleSnapshot; xhs?: StyleSnapshot };
  outlineVersions: OutlineVersion[];     // 本次 run 的全部提纲版本
  outlineVersionId: string | null;       // 当前生效的提纲版本
  status: "running" | "completed" | "failed" | "aborted";
  createdAt: number;
  finishedAt: number | null;
  nodes: Record<NodeId, AgentNodeState>; // 含 content / imageUrl / error / attempt / model / style / metrics
  summary: RunSummary | null;            // 终态才有值
  report: RunReport | null;              // 终态才有值
}
```

**断线重连策略**

浏览器 `EventSource` 自动重连，服务端在每次连接建立时立即下发全量快照。

- 节点已累积内容、耗时、token 用量全在快照里，重连后整体替换，不丢状态
- 终态写回 `RunState`，连到已经结束的 run 也能立刻拿到 `summary` 与 `report`
- **不做事件重放**：全量快照已能收敛状态，再维护事件日志表属于过度设计
- 事件带自增 `id` 仅用于排查时序，服务端不处理 `Last-Event-ID`

前端据此做了两处必要处理：

1. 快照 `status !== "running"` 时直接结束当前任务。批量模式原来只等 `run:done` 才 resolve，断线期间 run 结束会让整个队列永久卡住，这是本轮修掉的真实 bug
2. `onerror` 时显示「连接中断，正在重连」，收到新快照自动清除

策划节点失败时推送：

```
event: node:error
data: {"nodeId":"planner","message":"JSON 解析失败（已重试1次）"}
```

随后推送 `run:failed`，前端提示「策划提纲生成失败，无法继续生成内容」。

**5. 执行日志与报告**

每个节点在 `AgentNodeState.metrics` 上记录执行指标：

| 字段 | 含义 |
|---|---|
| `startedAt` / `endedAt` / `durationMs` | 首次开始到最终结束的总耗时，策划重试不重置起点 |
| `usage` | 该节点所有尝试累加后的 token 用量，含 prompt / completion / reasoning / cached |
| `usageEstimated` | true 表示服务端未返回 usage，按字符估算 |
| `retries` | 自动重试次数 = 尝试次数 - 1 |

token 来源：请求体带 `stream_options: { include_usage: true }`，方舟在流末尾补一片 usage。中间分片的该字段是 `null`，且解析必须放在 `choices` 判空之前，否则会漏掉。`completionTokens` **包含思维链 token**，所以「输出 token」可能远大于正文字数，报告里单独列出 `reasoningTokens` 说明差异。

流水线进入终态时由 `buildRunReport` 生成 `RunReport`，写回 `RunState.report` 并随 `run:done` 下发；也可以 `GET /api/run/[runId]` 一次性取全量快照与报告。

报告内容：

- 节点明细：模型、状态、尝试次数、耗时、输入/输出 token、重试次数
- 汇总：模型调用次数、token 合计、失败与中断数
- 并行加速比：4 个后置节点耗时之和 ÷ 并行阶段实际墙钟时间
- `hasEstimated`：任一节点用了估算值就置 true，前端明确标注

自动重试已下沉到 4 个后置节点：仅对网络异常、408、429、5xx 重试，`AbortError` 与其他 4xx 不重试。

## 模型分工（差异化）

不同平台使用擅长该文体的模型：

| Agent | 实际模型 id | 原因 |
|---|---|---|
| 策划 Agent | `deepseek-v4-1-flash-261017` | 结构化拆解和 JSON 输出稳定 |
| 长文 Agent | `deepseek-v4-1-flash-261017` | 擅长长文逻辑结构 |
| 脚本 Agent | `deepseek-v4-1-flash-261017` | 擅长分镜格式输出 |
| 小红书 Agent | `glm-5-3-flash-260828` | 与长文/脚本同速度量级，避免看板上显得没同步启动 |
| 配图 Agent（扩写） | `doubao-seed-2-1-pro-260915` | 中文视觉描述能力强 |
| 配图 Agent（出图） | `doubao-seedream-5-0-flash-260915` | 文生图专用，出图质量好 |

所有模型共用同一个方舟 API Key，仅通过 `model_id` 切换，不需要对接多个服务商。

## 三种运行模式

一次 run 始终是「1 个选题 → 1 条流水线」。批量能力由前端串行拉起多次 run 实现，每个 run 独立连一条 SSE。

| 模式 | 行为 | 请求差异 |
|---|---|---|
| 单次生成 | 一个选题跑一条流水线 | 只传 `topic`（可带 `styles`） |
| 批量选题 | 多行输入（最多 3 个）逐条跑 | 每条 run 传 `topic`（可带 `styles`） |
| 多版生成 | 同一选题跑 3 次，每次注入一个创作维度 | 额外传 `variant`（可带 `styles`） |

三种模式都可以额外传 `styles: { longform?, script?, xhs? }`，值为风格模板 id。风格模板与创作维度是两个正交维度：维度只影响策划提纲的结构，风格只影响下游三个文本 Agent 的写法，可以任意组合。

前端用 `tasks[]` 维护批量结果，每个元素含自己的 `nodes` 与 `runId`，tab 切换时只切展示数据源，不重连。

### 多版生成的差异化提纲

多版不是「同一份 prompt 跑三次」，而是**定向生成三种结构不同的提纲**。三个维度定义在 `lib/variants.ts`（纯数据，前后端共用）：

| 变体 | 定位 | 长文骨架 |
|---|---|---|
| 深度分析版 | 靠逻辑与证据说服 | 矛盾现象切入 → 论点+论据 → 反面观点与回应 → 可执行建议 |
| 故事化叙述版 | 靠人物与冲突代入 | 具体人物场景 → 冲突困境 → 转变过程 → 一句短观点 |
| 科普入门版 | 零基础，用类比降门槛 | 生活类比 → 分步拆解 → 常见误区 → 一句话总结 |

变体注入路径：

```
page.tsx (variant)
  → POST /api/run（isVariantKey 校验，非法返回 400）
  → createRun(topic, variant) 存入 RunState.variant
  → runPlanner 构造 new PlannerAgent(run.variant)
  → 构造函数把 promptBlock 追加到 system prompt
```

约束：**差异化必须落在结构骨架上**（段落推进步骤、论据类型、配图风格），只换形容词模型仍会输出同质提纲。下游 4 个 Agent 不额外感知变体，提纲已携带角度与结构。`variant` 为可选参数，不传时行为与单次模式一致；`rerunNode` 复用 `run.outline`，变体信息天然保留。

## 历史任务回看

流水线到达终态后，整份 `RunSnapshot` 落盘到 `data/runs/{runId}.json`，进程重启后仍可完整回看。

**批次模型**

- 多版模式一次点击创建的 3 个 run 共用同一个 `batchId`（前端生成）；单次模式的 `batchId` 等于 `runId`
- `GET /api/history` 读目录、按 `batchId` 聚合，按批次创建时间倒序返回最近 5 个批次
- 超出时整批淘汰，不会出现同一批次只剩部分版本
- 批次标题按选题是否相同区分：多版模式同一选题显示选题本身，批量选题模式显示「N 个选题」，版本按钮各自显示所属选题（悬停可看完整列表）

**为什么不用 localStorage**

前端存 runId 只能救「刷新页面」，救不了「进程重启」——`globalThis` 上的 Map 会清空。实际使用中主要场景恰恰是隔天再打开，所以必须服务端落盘。

**只记终态**

| 状态 | 是否落盘 | 原因 |
|---|---|---|
| `completed` / `failed` | 是 | 完整产出或完整失败报告都有复盘价值 |
| `aborted` | 否 | 内容不完整，进历史会误导 |
| `running` | 否 | 尚未收敛 |

**接口**

| 接口 | 说明 |
|---|---|
| `GET /api/history` | 最近 5 个批次的回看摘要（批次 → 版本列表） |
| `GET /api/run/[runId]` | 先查内存，未命中回退读 `data/runs/`，返回结构不变 |

**前端回看态**

点击历史版本后回填结果区，顶部显示「历史回看」横幅；隐藏单节点重跑入口，不建立 SSE 连接。点「退出回看」或切换模式恢复到空态。想接着改则用同一行的「继续迭代」，见下节。

**边界**

- 写盘失败只 `console.error`，不影响流水线结果
- 部署到 Vercel 等只读环境时该功能自动降级为不可用
- 落盘内容是完整文本，单条约 10–40 KB，5 批上限下磁盘占用可忽略

## 平台风格模板库

原先三个渠道的写作风格硬编码在各自 Agent 的 system prompt 里，用户想换文风只能改代码。本轮把「文风」抽成可管理的运行时输入：提纲决定写什么，风格模板决定怎么写。

**数据模型（`lib/styles.ts`）**

- `StyleChannel = "longform" | "script" | "xhs"`，一个渠道对应一个下游文本节点
- `StyleTemplate { id, channel, name, summary, prompt, builtin, createdAt, updatedAt }`
- `prompt` 是「文风 / 格式 / 排版 / 标签」的自然语言描述，只作为提示词内容，不参与任何逻辑判断
- 内置 6 套模板（每渠道 2 套）写在代码里，永远可用；`builtin: true` 只读，可「复制为自定义模板」后再改

**存储与接口**

自定义模板落盘 `data/styles.json`，与历史快照同一套容错思路：写盘失败只记日志，不影响流水线。

| 接口 | 说明 |
|---|---|
| `GET /api/styles` | 内置 + 自定义全量列表，前端按渠道过滤 |
| `POST /api/styles` | 新建自定义模板 |
| `PUT /api/styles/[id]` | 编辑自定义模板，内置模板返回 403 |
| `DELETE /api/styles/[id]` | 删除自定义模板，内置模板返回 403 |

校验规则：名称 ≤ 24 字、说明 ≤ 60 字、内容 ≤ 2000 字、渠道必须合法、同渠道不允许重名、自定义模板上限 30 套。

**注入路径**

```
page.tsx (styles: { channel: templateId })
  → POST /api/run（resolveStyles 解析成快照，模板不存在或渠道不符返回 400）
  → createRun(topic, variant, batchId, styles) 存入 RunState.styles
  → runTextNode(..., styles[channel])
  → buildSectionInput：选题 + 专属提纲 + 风格块
```

风格块放在入参末尾，并明确「与默认写作习惯冲突时以模板为准」，避免 Agent 自身的 system prompt 与模板各说各话。

**为什么存快照而不是存 id**

模板随时可能被编辑或删除，但已经跑完的任务必须能解释「当时用的哪套文风」。所以 `RunState.styles` 存 `{ id, name, prompt }` 快照，节点上再存 `{ id, name }` 供卡片徽标与报告展示；历史回看读的是落盘快照，不受模板后续变动影响。单节点重跑复用同一份快照。

**前端**

- header「风格模板」按钮 → 三栏面板（公众号 / 短视频 / 小红书），支持新建、编辑、删除、复制
- 运行控制台三个下拉，分别对应三个下游 Agent；运行中锁定，随 run 快照落盘
- 卡片标题下显示「风格 · xxx」徽标，执行报告新增「文风」列

## 提纲人工干预与版本回退

策划 Agent 生成提纲后，提纲原本是只读的：不满意只能整条流水线重跑，策划和 4 个下游全部重新调用，既费 token 也费时间。本轮把提纲变成可编辑、可回退的运行时数据。

**版本链模型（`lib/orchestrator.ts`）**

```ts
interface OutlineVersion {
  id: string;        // v1 / v2 …
  label: string;     // 策划原始 / 手动编辑
  source: "planner" | "manual";
  createdAt: number;
  outline: unknown;  // 完整提纲 JSON
}
```

- `RunState.outlineVersions` 保存本次 run 的全部版本，`activeOutlineVersionId` 指向当前生效版本
- `run.outline` 仍是「当前生效提纲」，单节点重跑与下游入参都读它，原有逻辑不变
- 版本链随 `RunSnapshot` 下发并落盘，历史回看也能看到当时的全部版本
- 每个 run 独立维护版本链，多版模式 3 个 run 互不影响

**接口**

| 接口 | 说明 |
|---|---|
| `POST /api/outline/[runId]` | 提交编辑后的提纲或回退版本，局部重生成下游 |

请求体只需 `{ outline: <完整提纲对象> }`。服务端按顺序处理：

1. run 不存在 → 404；策划未完成、提纲结构非法、内容无变化 → 400；有节点在跑 → 409
2. 按 `longForm / script / xhs / image` 逐渠道做 `JSON.stringify` diff
3. 有变化：内容与某个历史版本完全一致时直接激活该版本（回退不新增版本），否则追加 `vN 手动编辑`
4. 只重置受影响节点并重新调度，其余节点 `content / imageUrl / metrics` 原样保留
5. 重新生成报告并落盘，返回 `{ version, versions, affected }`

**前端交互（策划卡展开态）**

- 「编辑提纲」进入编辑态：当前版本格式化成 JSON 放进 textarea，实时校验语法，非法时提交按钮禁用
- 编辑区上方是版本 chips（`v1 · 策划原始 · 当前`、`v2 · 手动编辑 小红书`），点任意版本即载入编辑器，实现回退预览
- 主按钮「基于当前提纲重生成下游」，提交后重连 SSE 观察本次局部重生成
- 历史回看态只读，可查看版本链但不能编辑；运行中可编辑文本，提交按钮锁定

**提交前影响面预览**

编辑态边打字边比对草稿与当前生效版本，直接显示「将重跑：小红书笔记」，提交前就能判断代价。比对逻辑抽在 `lib/outline-diff.ts` 的 `diffOutlineChannels(prev, next)`，前端预览与服务端调度共用同一份实现——两边各写一遍迟早会漂移，出现「预览说只跑小红书、提交后却跑了长文」。

- 四个渠道全一致 → 「与当前版本一致，修改后才能提交」
- 只改了顶层 `topic` → 「只改了选题：选题变化不影响四个渠道，请修改至少一个渠道后再提交」，服务端同样拒绝并返回这句文案
- 有渠道变化 → 列出将重跑的全部渠道，按钮可提交

**版本 chips 区分改动渠道**

`OutlineVersion.affected?: NodeId[]` 记录该版本提交时实际重跑的渠道，chip 上显示短名（`v3 · 手动编辑 小红书`），悬停可看完整渠道名与提交时间。策划原始版本没有该字段，旧快照缺字段时直接不显示，不需要数据迁移。回退到某个旧版本时，chip 展示的仍是它当初改动过的渠道。

**边界**

- 只改 `topic` 不触发任何渠道变化，接口明确拒绝，避免产生「看起来提交了但什么都没发生」的版本
- 「变化」按渠道片段序列化结果判定，改一个标点也算变化
- 局部重跑后报告里未受影响节点沿用上一轮指标；整体墙钟时间仍是 run 创建到最终结束的跨度

## 续跑与会话恢复

只读回看解决了「看得到」，但没解决「接着改」：历史批次里的 run 只在磁盘上，`编辑提纲` 与 `重跑` 都被锁死。续跑能力把落盘快照重新回灌进内存，让旧任务回到可编辑状态。

**回灌模型（`lib/orchestrator.ts`）**

`resumeRun(snapshot)` 用 `HistoryFile` 重建 `RunState`：

- `nodes` 用 `structuredClone` 深拷贝，避免后续重跑改到快照对象
- `outline` 取 `activeOutlineVersionId` 指向的版本，版本链原样保留
- `subscribers / controllers` 置空 —— 回灌只恢复状态，不启动任何节点
- 内存里已有同 runId 时直接复用，接口天然幂等

**接口**

| 接口 | 说明 |
|---|---|
| `POST /api/run/[runId]/resume` | 把内存或磁盘上的 run 接回可编辑视图，不触发任何模型调用 |

内存命中直接返回快照；未命中读 `data/runs/{runId}.json` 回灌；都没有返回 404。

**前端入口**

- 历史面板每个版本旁新增「继续迭代」：接回后可编辑提纲、局部重生成，改动只重跑受影响的渠道
- 继续迭代沿用原 `runId` 与 `batchId`，因此历史里是**原地更新**，不会产生重复批次

**刷新自动恢复**

`localStorage` 记 `cab-last-run`（模式 + runId + 选题），只存 ID 不存内容，快照仍从服务端读：

| 刷新时的状态 | 行为 |
|---|---|
| 有任务仍在 `running` | 直接接回并重连 SSE，顶部提示「已接回刷新前的运行」 |
| 全部已结束 | 不抢屏，控制台上方出现「上次任务 … 继续查看 / 忽略」提示条 |
| 快照已过期（> 24h）或读不到 | 静默清除本地记录 |

批量模式按已创建的任务逐个恢复；刷新发生在队列中间时，未启动的任务不会被凭空补出来，避免出现永远待跑的 tab。

**边界**

- 回灌不产生事件流，只有 `running` 状态的快照才会连 SSE
- 回灌后重新生成仍走 `regenerateFromOutline`，鉴权、diff、版本复用规则完全一致
- 进程重启后内存 Map 为空，但磁盘快照仍在，`resume` 会走读盘分支，续跑能力不受影响
- 会话记录只用于「接回界面」，不参与任何业务判断；隐私模式下写入失败不影响主流程

## 成品库

历史批次只保留最近 5 批，`导出全部` 与 `复制` 又都是一次性动作。用户真正想留下的产出需要一个与 run 解耦的长期存放点，成品库按「内容卡片」保存，删历史不影响它。

**数据模型（`lib/library-model.ts` / `lib/library.ts`）**

| 字段 | 说明 |
|---|---|
| `id` | `runId:nodeId`，同时是幂等键 |
| `nodeId` | 只允许 `longform` / `script` / `xhs` / `image`，策划提纲属于过程数据 |
| `content` / `imageUrl` | 正文与配图地址 |
| `topic` / `variant` / `styleName` / `model` | 展示与追溯用 |
| `savedAt` | 保存时间，列表按它倒序 |

落盘 `data/library.json`，上限 200 条，超出淘汰最旧。用户主动保存的产出比历史批次珍贵，容量放宽但仍保留上限，避免无限增长。

**接口**

| 接口 | 说明 |
|---|---|
| `GET /api/library` | 按保存时间倒序列出全部成品 |
| `POST /api/library` | body `{ runId, nodeId }`，从服务端快照取正文入库；同一张卡重复保存原地更新 |
| `DELETE /api/library/[id]` | 按 `runId:nodeId` 删除，不存在返回 404 |

**为什么不信任前端正文**

入库接口只收 `runId + nodeId`，正文一律从 `getRun` / `loadRunSnapshot` 取。否则前端回看旧快照、正文被裁剪或改动，都会让成品库与实际产出对不上。

**前端入口**

- 头部「成品库 (n)」，面板标题旁显示「已存 n / 200 条」，右上角「收起」直接关闭面板
- 已完成的内容卡右上角固定「收藏」按钮，展开、折叠、滚动位置都不影响可见性；展开后操作栏也有完整入口
- 历史回看态同样可收藏：后端按 runId 读磁盘快照，不要求 run 在内存里

**边界**

- 成品库与历史互不影响：删历史批次不删成品，成品库满额只淘汰自己最旧的条目
- 图片节点要求 `imageUrl` 已生成，文本节点要求正文非空；未完成节点返回 400

## 项目库（整批收藏）

成品库解决「某一路我满意」，项目库解决「这一整条流水线我都想留着」：选题、提纲、四个渠道的正文与配图打包成一个项目整体保留，删历史不影响。两者独立落盘、独立淘汰，不互相自动生成。

**数据与接口**

- 存储：`data/projects.json`，容量上限 `PROJECT_MAX_ITEMS = 50`（每条含长文全文，体积远大于单卡片）
- id 用 `runId`，重复收藏只更新 `savedAt`，不产生第二条
- `POST /api/projects` 接收 `{ runId }`，正文与提纲一律从服务端快照取
- 入库要求四个内容渠道全部 `completed`：文本节点正文非空、配图节点已出图，否则 400
- `GET /api/projects` 返回按 `savedAt` 倒序的列表；`DELETE /api/projects/[id]` 删除，不存在返回 404

**前端入口**

- 「执行监视」标题行右侧新增「收藏整个项目」，仅四路全部完成时可用
- 成品库面板内用 tab 切换「卡片 / 项目」，头部数量是两者合计
- 项目条目展示选题、保存时间、四路预览（渠道名 + 风格 + 正文首行），操作有「下载全套」（含选题+四路的单个 md）与「移除」

**与成品库的关系**

- 同一 run 可以既收藏整张卡，也收藏整个项目，互不影响
- 两者容量与淘汰策略独立，项目库满了只淘汰最旧的项目

## 批量结果横向对比

批量/多版模式默认用 tab 展示任务，一次只能看一个。当需要在多个选题或多个变体之间挑出最优产出时，来回切 tab 靠记忆对比成本很高。

**入口与视图**

- 批量 tab 行右侧新增「横向对比」按钮：批量/多版模式下**始终渲染**，`tasks.length < 2` 时置灰并给出 `title` 说明为什么不可用
  - 早期版本直接隐藏按钮，实测反馈是「看不到、也不知道怎么才能看到」；按钮消失等于功能不可发现，所以改成置灰
- 开启后把单任务卡片网格替换为一张对比表：行 = 4 个内容渠道（长文 / 脚本 / 小红书 / 配图），列 = 任务
- 整个对比是纯前端视图，直接读内存里的 `tasks[].nodes`，不新增接口、不请求后端

**单元格交互**

- 文本格：正文前两行截断，hover 时浮出全文预览（`pointer-events: none`，不挡住点击）
- 配图格：缩略图 + 「查看原图」
- 复制/下载按钮在格内，`stopPropagation` 避免误触发跳转
- 点击单元格或列头选题：切回该任务的 tab 并关闭对比视图，看完整内容
- 未完成的格子显示「未完成」，不参与对比

**横向滚动**

- 表格外层是 `overflow-x-auto` 容器，每列 `min-width: 14rem`；任务多时出现横向滚动条，不会挤压列宽

## 提纲编辑的撤销 / 重做

提纲编辑器是一整块 JSON 文本域。改错时原来只有两条出路：手动改回去，或者点版本 chip 重新载入——后者会连同本次所有未提交的修改一起丢掉，粒度太粗。

**实现**

- 历史栈放在 `useRef`，避免每次输入都触发重渲染；`canUndo / canRedo` 单独用 state 驱动按钮态
- **只在 `blur` 时记录**一次，且与栈顶内容相同的草稿不记——光标进出不占格
- 栈上限 20 条（`OUTLINE_HISTORY_LIMIT`），超出丢最早的一条
- 在历史中间继续编辑会截断「未来」分支，与常见编辑器行为一致
- 纯前端、纯草稿文本：不落库、不上后端、不触发任何模型调用

**快捷键与焦点**

- `Ctrl/Cmd+Z` 撤销，`Ctrl/Cmd+Shift+Z` 重做
- **焦点在文本域内时不接管**，交给浏览器原生撤销——字符级粒度更符合编辑直觉；焦点在编辑区外才走历史栈

**清空时机**

| 时机 | 处理 | 原因 |
|---|---|---|
| 点版本 chip 切换版本 | 用该版本内容重新做栈底 | 换版本是新会话，旧历史不该带过来 |
| 提交成功 | 清空 | 编辑会话已结束，栈随之作废 |
| 切换任务 tab | 清空 | 草稿归属变了，避免撤销到上一个任务的内容 |
| 取消编辑 / 新任务 / 进入回看 | 清空（`resetOutlineEditor` 内） | 同上 |

## 左侧边栏导航

页面从「单列纵向」改为「左侧边栏 + 右侧主内容区」。侧边栏只承担导航：读的都是已有 state，没有新增数据通道，因此不可能与主区状态不一致。

**布局**

- 展开 264px / 收起 68px，`width` 过渡；右侧列 `min-w-0 flex-1`，原 header 与 main 的内部结构不动
- 3D 场景仍在最底层，侧边栏 `sticky top-0 h-screen`，主内容区独立滚动
- 收起态只留图标（CA 徽标、状态点、单字菜单图标），再点 CA 徽标展开
- 折叠状态只在本次会话内保持：持久化需要在 effect 内 setState，会新增 lint 报错，而它只是界面偏好，刷新恢复展开的代价可以接受

**任务列表**

- 数据源 = 本次会话任务（单次模式取当前 run，批量/多版取 `tasks`）+ 服务端最近 5 批历史的 run 级条目
- 历史按批次分组：组标题是选题名（批量批次为「N 个选题」）加时间，组内列各 run，不再平铺成十几条
- 当前会话的 runId 若已落盘，从历史段剔除，避免同一条任务出现两次
- 每条展示标题、标签、时间、状态点；标签位暂用创作维度/模式代替（多版=维度名、批量=任务 label、单次=「四路并行」），因为现有 run 没有真实平台字段
- 点击条目 = 只读回看（当前会话条目改切 tab 视角）；历史条目右侧的「迭代」按钮复用 `resumeHistoryRun` 接回可编辑视图
- 选中态由「当前 run / 当前 tab / 回看 runId」三者之一判定
- 新建任务写入 `tasks` 后列表自动出现，不需要额外的同步逻辑

**历史入口只有一处**

右上角原来的「历史记录」按钮与批次面板已下线，能力全部并入侧边栏：批次聚合变成组标题，继续迭代变成条目上的「迭代」，刷新由首屏加载与流水线结束后的 `loadHistory` 负责。同一份历史数据不再有两个入口、两套呈现。

**清空撤销栈**

侧边栏切任务与切 tab 走同一条规则：先 `clearOutlineHistory()`。历史回看路径还会经过 `resetOutlineEditor()`，同样清空。草稿归属一变，旧历史就不能带过去。

**功能菜单与状态**

- 新建流水线任务：运行中禁用并在 `title` 说明原因；点击后清空当前结果、回到输入区顶部，历史与成品库不受影响
- 风格模板库：复用现有 `stylePanelOpen` 面板，不复制一套模板 UI
- 设置：轻量弹层，只放「侧边栏收起 / 重看引导 / 清空本地会话记录」，不碰服务端数据
- 底部 API 状态：复用 `GET /api/history` 做 30s 轻探测，页面重新可见时立即补测；探测完成前显示「检测中」，不预判离线

## 关键设计决策

1. **编排引擎自研**：场景是固定的「策划 → 4 路并行」，不需要 LangGraph 的条件分支能力，自研状态机更轻量、更易讲解。
2. **SSE 而非 WebSocket**：只需要后端向前端单向推送状态和内容，SSE 足够且更简单。断连重连用「全量快照收敛」而不是事件重放：服务端在每次连接建立时下发 snapshot，终态写回 `RunState`，所以连到已结束的 run 也能立刻拿到 summary 和 report；事件带自增 id 仅用于排查时序，不处理 `Last-Event-ID`。
3. **看板用卡片网格，不用节点画布**：曾尝试 React Flow 做节点画布，实测否决——4 个内容节点摆成 2×2 会暗示「长文 → 脚本 → 小红书 → 配图」的先后顺序，而它们实际完全并行，布局在误导架构；拖拽时画布平移还会抢走节点拖拽事件。改为「策划卡整行 + 4 张内容卡一行四列」，同样表达 1 上游 + 4 并行，且更省空间。
4. **结果卡片默认折叠，运行时自动展开**：默认折叠让看板紧凑，但节点开始运行时必须自动展开——否则 4 个 Agent 并行流式吐字这个核心能力在界面上看不见。展开态内容区固定 `max-h` + `overflow-auto`，滚动限制在卡片内，不让页面高度暴涨。
5. **中断逻辑**：每个 Node 单独持有独立的 AbortController，不共用全局 signal；abort 只切断 LLM 流式请求，不清空 node.content。具体规则：
   - **全局中断（策划阶段）**：策划节点停止生成，已输出内容保留并标记为 `cancelled`；4 个后置节点状态标记为 `cancelled`，不再启动。
   - **全局中断（并行阶段）**：策划节点已完成保持不动；已完成的节点内容保留不动；正在流式输出的节点立刻停止拉取新 token、已生成文字保留；还没启动的 pending 节点标记为 cancelled，不再启动。
   - **单节点中断**：仅指定节点停止生成、已有内容保留；策划及其他所有节点不受影响，正常跑、内容保留；其他 pending 节点继续正常调度执行。
6. **执行报告随快照落盘**：报告由 `buildRunReport` 在内存中生成，写回 `RunState.report`，随 `run:done` 下发，并可通过 `GET /api/run/[runId]` 取。最初只在内存保留、不写文件；新增历史回看后改为随快照落到 `data/runs/`——内存态在进程重启后必然丢失，而「隔天打开看上一轮结果」正是回看的主要场景。该目录已加入 `.gitignore`，不污染仓库；写盘失败只记日志，不影响流水线。报告里刻意保留 `hasEstimated` 标记：服务端没返回 usage 时宁可标注「估算」，也不把估算值当真实值展示。
7. **并行加速比作为架构价值的量化指标**：报告不只列各节点耗时，还计算「4 路串行耗时之和 ÷ 实际墙钟时间」。这是唯一能用一个数字说明「多 Agent 并行」比单线程串行快多少的地方。
8. **历史记录按批次限流，而不是按 run**：多版模式一次点击产出的 3 个 run 属于同一个 `batchId`。若按 run 限 5 条，两批就把名额吃光；按批次限 5 个，回看时也正好是「一批 3 个版本」的对比单元。淘汰时整批删除，不会出现同批只剩一半版本。
9. **风格模板按 run 存快照，而不是只存模板 id**：模板可编辑可删除，历史任务却需要长期可解释。存 `{ id, name, prompt }` 后，模板后续怎么变都不影响已完成的 run，回看时能还原当时的完整入参。代价是快照体积增加约 1 KB/渠道，相对于正文可忽略。
10. **内置模板只读，改内置走「复制」**：允许直接编辑内置模板会导致演示环境的默认文风被改坏且无法回到初始状态。只读 + 复制既保证默认可用，又保留了自定义空间；存储层同时兜底，即使手改 `data/styles.json` 把 `builtin` 改成 true 也会被强制改回 false。
11. **提纲版本链 + 渠道级 diff，而不是重跑全部下游**：人工改提纲通常只动某一个平台的写法，把 4 个下游全部重跑既浪费 token，也会把已经满意的小红书、配图产出覆盖掉。按渠道 diff 后只调度受影响的节点，未改动节点连指标都不动；版本链则保证每次提交都能回退，且提交内容与历史版本一致时直接复用旧版本，避免回退把版本列表刷爆。
12. **历史批次「原地续跑」，而不是克隆新任务**：回灌 `RunState` 并复用原 `runId` / `batchId`，历史里是同一批次原地更新。克隆虽然能保留基线，但会让「隔天打开、微调一句、再发一次」这个高频动作批量消耗历史名额，且用户实际关心的是「这篇更新后的内容」，不是并排对比两个版本。落盘快照本身已是终态，回灌不会启动任何节点，只有用户真正提交提纲时才会调用模型。
13. **渠道 diff 前后端共用一份实现**：影响面预览如果在前端另写一套比对，哪怕规则只差一个边界（比如把 `topic` 算进渠道），用户就会看到「预览说重跑小红书、实际跑了长文」。把 `diffOutlineChannels` 抽到 `lib/outline-diff.ts`，前端只负责渲染结果，服务端仍是唯一调度方，预览天然不会与执行脱节。
14. **成品库按卡片保存，且正文只从服务端取**：历史是「过程记录」，成品库是「内容资产」，两者生命周期不同，所以独立存储、独立淘汰。入库接口只收 `runId + nodeId`，正文由服务端从内存或落盘快照读取——如果允许前端传正文，回看态裁剪过的文本、被手动改过的内容都会悄悄进库，成品库就不再可信。`id = runId:nodeId` 让重复保存天然幂等，用户连点两次只是更新时间。
15. **项目库与成品库分库，而不是在成品库里加「整批」类型**：两者容量差 4 倍（200 vs 50）、展示粒度不同（单路 vs 四路）、淘汰语义不同。硬塞同一个列表会让排序、上限、空态文案都出现两套分支。分库后各自的淘汰与界面都能保持简单，用户也能在面板里用 tab 一眼区分「我收藏的单路」和「我收藏的整批」。
16. **横向对比是纯前端视图，不新增后端接口**：批量任务的四路正文已经完整存在于前端 `tasks[].nodes` 里，再做一个「对比快照」接口只是把内存里的数据搬到服务端再搬回来，徒增一次往返与一个落盘入口。直接在前端把卡片网格换成表格，数据零拷贝、状态零新增（只加一个 `compareView` 布尔），切换对比不会改变当前选中的任务。
17. **撤销按「失焦快照」记，且不抢文本域的原生撤销**：逐字符记录会产生几十条无意义的中间态，撤销一次只退一个字符；按 `blur` 记整段草稿，一次撤销退一次完整修改，符合「改完一段再回退」的实际节奏。焦点在文本域内时不接管 `Ctrl+Z`，把字符级撤销留给浏览器，避免用户习惯了原生行为后觉得我们的实现「退得太狠」。
18. **侧边栏只读现有状态，不新增数据通道**：任务列表由 `tasks`、当前 run、`historyBatches` 三类已有数据拼出来，没有新增接口，也没有新增持久化。这样侧边栏与主区读的是同一份 state，不会出现「列表里已完成、主区还在跑」的两套事实。折叠态刻意不落 localStorage：读取它需要在 effect 里 setState，会新增 lint 报错，而它只是界面偏好，不值得为刷新保持多付这个代价。
19. **一个功能只留一个入口**：侧边栏落地后发现右上角「历史记录」与它重复，保留两处的代价不是多点一次，而是用户在两个地方看到不同的任务数量与不同的动作（批量 tab 只能回看、历史面板能继续迭代）。因此删掉 header 入口与整块面板，把批次聚合和继续迭代搬进侧边栏，历史数据只有一个出口。
