# Round 09 — 阶段 6：最近 5 次任务历史回看

## 我的提问（用户视角）

反复测试这套内容生产系统时发现一个痛点：任务跑完、页面刷新或者 SSE 重连之后，刚才生成的提纲、文案、脚本就找不回来了。想对比之前跑过的多版内容、复盘上一轮效果，只能重跑一遍完整流水线，既费 token 又费时间。

所以规划新增：**最近 5 次流水线任务历史回看**，可以直接调取历史任务的完整运行信息与产出，支持快速回看、对比不同批次的内容方案。

## AI 的评审意见（指出一个隐藏前提）

方案方向成立，但有一个必须先补的前提，否则只解决一半问题：

- **只在前端存 runId 不够**。Run 状态存在 `globalThis` 的 Map 里，进程一重启就清空。而「隔天打开项目」恰恰是最主要的回看场景——那时 dev server 早已重启过，历史列表点开全是 404。刷新页面能救回来，关机重启救不回来。
- 结论：**必须服务端落盘**。

同时提了三个设计取舍：

1. 只持久化终态 run，运行中和主动中断的不写盘——半成品进历史反而误导。
2. 写盘失败不影响主流程，磁盘异常只 `console.error`。
3. 回看态只读：不挂「停止」，不订阅 SSE，想复用内容就重跑新建 run。

还有一个预判风险：`data/` 在项目根目录下，Turbopack 的文件监听可能把它当源码变更触发重编译，需要实测。

## 我的确认与决策过程

AI 给了两个必须拍板的点，我选了推荐项：

| 决策点 | 选择 | 理由 |
|---|---|---|
| 「最近 5 次」计数单位 | 5 个批次 | 多版模式一次产出 3 版，按 run 计数跑两批就吃光名额；按批次才算「对比不同批次」 |
| 对比形态 | 快速切换回看 | 先解决「找不回」，并排双栏会重写结果区布局，成本高且现有卡片已有折叠 |

## 实现

**批次模型**

- 前端每次点击生成一个 `batchId`，批量模式下的 3 个请求共用
- 单次模式不传，服务端默认 `batchId = runId`
- 落盘仍按 `data/runs/{runId}.json`，文件内记录 `batchId`
- `GET /api/history` 读目录后按 `batchId` 聚合，按批次时间倒序取前 5

**淘汰策略**：超出时**整批删除**，不是逐个文件删。否则同一批次可能只剩 1~2 个版本，回看时会误以为当初就少生成了。

**接口**

| 接口 | 变化 |
|---|---|
| `GET /api/history` | 新增，返回批次列表 |
| `GET /api/run/[runId]` | 先查内存，未命中回退读磁盘，返回结构不变 |

**前端**：header 右侧「历史记录 (N)」按钮 → 批次面板 → 点版本回填结果区 → 蓝色「历史回看」横幅 + 退出回看。回看态隐藏单节点重跑，切换模式自动退出回看。

## 验证

| 验证项 | 方法 | 结果 |
|---|---|---|
| 落盘 | 跑完整流水线后检查 `data/runs` | 142s 后生成，单文件 10.7 KB，5 个节点 + report 齐全 |
| 重启后回读 | kill 进程后重启，`GET /api/run/{id}` | 200，status=completed，report 存在（内存必然已空） |
| 批次聚合 | 伪造 3 个同 `batchId` 快照 | 聚合成 1 批 3 版本，变体名正确 |
| 淘汰 | 造 6 个假批次 + 跑 1 次真实任务 | 8 个批次收敛到 5，整批删除最早的 3 批 |
| 前端交互 | 浏览器实测 | 历史面板、回看横幅、卡片内容、退出回看 5 项全 PASS |

**一个测试过程中的坑**：用 PowerShell `Invoke-RestMethod` 发中文 topic，落盘后码点全是 `0x3F`（问号）。一开始怀疑是应用编码问题，查了正文内容的码点——`0x5468 0x4e00 0x4e0a...` 全是正常汉字，说明落盘链路没问题，是 PowerShell 发送时按 ANSI 编码把请求体弄坏了。改用 `UTF8.GetBytes` 传 byte[] 重测，topic 码点 `0x8fdc 0x7a0b 0x529e 0x516c`（远程办公）正常。

**结论**：这是测试脚本的问题，不是产品问题。但值得记下来——验证编码问题时，要区分「输入坏了」和「链路坏了」，否则会去修一个不存在的 bug。

## 反思

- 用户提需求时说的是「历史记录」，很容易直接去做 localStorage。但顺着场景多问一句「隔天打开时进程还在吗」，就会发现内存态早就没了。**功能能不能真正解决问题，取决于它落在哪个存储层上**。
- 淘汰策略这种细节容易被忽略：以「条」为单位删除，比以「批次」为单位删除实现简单一行，但会制造「这批怎么少了一版」的困惑。凡是有聚合关系的数据，删除也要按聚合单位来。
