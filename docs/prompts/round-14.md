# Round 14 — 阶段 11：成品库

## 我的提问（用户视角）

跑完一条流水线，满意的长文想留着以后用，但只有两条路：当场复制走，或者留在历史里。复制是一次性的，历史只保留最近 5 批、淘汰时整批删掉，「上周那篇改得不错的公众号」很容易连影子都没有。导出全部也只是把当前批次打个包，同样不解决长期留存。

所以我想要一个「主动存下来、以后还能找到」的地方，和流水线过程分开。

## AI 的评审意见

这是「缺失能力」而不是手感问题：现在的系统没有任何一个对象表示「我认可这份产出」。历史记录表达的是「执行过什么」，导出表达的是「此刻带走什么」，两者都不承担内容资产的角色。

设计上有四个点必须先定，否则做出来会变成历史记录的第二个副本：

1. **存什么粒度**：整批 or 单张卡。整批保存会把不满意的三个渠道也一起存进去，用户还得二次清理；按卡片保存，用户只需要标记自己认可的那一份。
2. **正文从哪来**：前端传 or 服务端取。前端在回看态展示的是快照内容，如果入库时让前端把文本回传，任何渲染裁剪或手动改动都会静默写进库，成品库就失去可信度。
3. **怎么去重**：同一张卡反复点保存不能产生多条。用 `runId:nodeId` 做 id，保存即 upsert。
4. **与历史的关系**：共用存储会让「删历史」连带删成品。两者生命周期不同，必须独立落盘、独立淘汰。

## 我的确认与决策过程

| 决策点 | 选择 | 理由 |
|---|---|---|
| 存储位置 | 独立 `data/library.json` | 与历史解耦，历史淘汰不影响成品；也避免改历史文件结构 |
| 保存粒度 | 单张卡片 | 用户认可的是某个渠道的产出，不是整批 |
| 正文来源 | 服务端从 run 快照读 | 不信任前端正文，保证库里内容与实际产出一致 |
| 去重方式 | `id = runId:nodeId`，保存即更新 | 重复点击天然幂等，不需要额外的确认弹窗 |
| 容量上限 | 200 条，淘汰最旧 | 主动保存的产出比历史珍贵，容量放宽；但必须有上限 |
| 入口位置 | 头部「成品库 (n)」+ 卡片内「存入成品库」 | 保存动作贴着产出，查看动作放在全局入口 |

## 实现

**数据契约（`lib/library-model.ts`，新增）**

`SavedItem`、`SAVABLE_NODE_IDS`、`LIBRARY_NODE_NAMES`、`isSavableNodeId`。单独拆出来的原因：`lib/library.ts` 依赖 `node:fs`，不能被打进客户端包，而前端需要用同一份类型和渠道名。

**存储（`lib/library.ts`，新增）**

- 落盘 `data/library.json`，上限 200 条
- 读盘失败（文件不存在、内容损坏）一律当空库，不让读盘问题冒到接口层
- `saveToLibrary(snapshot, nodeId)` 从快照组装条目，`id` 冲突时替换并置顶

**接口**

| 接口 | 行为 |
|---|---|
| `GET /api/library` | 按 `savedAt` 倒序返回 `{ items }` |
| `POST /api/library` | body `{ runId, nodeId }`，内存未命中回退读盘；未完成节点 / 图片未出图 / 正文为空返回 400，未知 run 返回 404 |
| `DELETE /api/library/[id]` | 删除成功 `{ ok: true }`，不存在 404 |

**前端（`app/page.tsx`）**

- 头部新增「成品库 (n)」，首次进页面与历史一起拉取
- 面板列出渠道、选题、保存时间、风格与两行预览，操作有复制 / 下载 / 移除
- 面板标题旁显示「已存 n / 200 条」，右上角「收起」直接关闭
- 已完成的内容卡底部新增「收藏到成品库」，展开与折叠态都可见，保存中禁用
- 下载：文本存成 `选题-渠道.md`，图片走原图下载
- `.gitignore` 增加 `data/library.json`

## 用户实测后的修正

第一版交付后，用户提出三个问题，暴露的是「功能存在但不可发现」：

1. 不知道在哪里收藏——按钮只在展开态显示，且混在复制/重跑一排按钮里
2. 不知道容量——上限写在文档里，界面没有任何提示
3. 不知道如何退出面板——只能再点一次头部按钮，没有显式关闭入口

修正：折叠态也渲染「收藏到成品库」；面板标题旁显示「已存 n / 200 条」，并说明超额淘汰规则；右上角新增「收起」。容量常量 `LIBRARY_MAX_ITEMS` 收进 `library-model.ts`，前后端共用同一个数字，避免界面写死 200 与服务端漂移。

第二次反馈（附截图）说明第一版修正仍不到位：折叠态按钮在卡片正文底部，长卡片一屏放不下，用户滚到内容中部时按钮在上方视野之外，实际仍然「看不见」。按钮放哪不是布局微调，而是发现性问题——最终把入口固定在卡片头部右侧，与展开/折叠、滚动位置都无关；展开后的操作栏保留完整入口。原折叠底部的按钮删除，避免同一张卡出现两个收藏按钮。

## 反思

- 这轮真正的设计点不是"加一个列表"，而是把「过程记录」和「内容资产」区分开。只要复用历史存储，用户删历史时就会连带丢掉成品，而这种耦合在演示阶段几乎不会被发现。
- 正文只从服务端取，短期看是多一次读盘，长期看是保住了成品库的可信度：库里存的永远是 Agent 的真实产出，不是某个界面状态。
- 200 条上限目前只是防无限增长，没有做「按容量预警」。如果以后接真实用户，应该补一个「快满时提示清理」，而不是静默淘汰。
