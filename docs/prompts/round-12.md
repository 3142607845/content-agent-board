# Round 12 — 阶段 9：历史续跑与会话恢复

## 我的提问（用户视角）

这次不是提需求，而是让我以真实使用者身份把产品完整跑一遍，找出用着不顺手的地方。

实测一轮后确认的问题：

1. 历史批次完全只读。展开任何一张卡只有「复制」，「重跑」是禁用且没有说明，「编辑提纲」干脆不渲染。上一轮做的提纲版本链只在新跑完的那一次有效，第二天打开历史批次就退化成纯展示。
2. 刷新页面就丢进程。runId 不落本地，跑到一半按 F5 直接回到空白控制台，没有「继续上次运行」入口，2 分钟的运行期间完全看不到进度。
3. 编辑态看不到影响面。提交前不知道会重跑哪几路，改完才发现只动了一路或者全跑了。
4. 只改顶层 `topic` 会被判「没有变化」，与直觉冲突。

选定本轮范围：**续跑能力**——历史批次可接回继续迭代 + 刷新后自动恢复。

## AI 的评审意见

问题的根因不在前端按钮，而在「落盘快照只是展示数据，没有回到运行态的通路」：`GET /api/run/[runId]` 读盘后只是把 JSON 返回给前端渲染，`regenerateFromOutline` 却要求 run 在内存 Map 里，两者之间缺了一层回灌。

所以方案是补一个 `resumeRun`：把 `HistoryFile` 重新构建成 `RunState` 塞回内存，`subscribers / controllers` 置空，不启动任何节点。这样历史任务就和新跑完的任务完全等价，编辑提纲、局部重生成、单节点重跑全部复用现有逻辑，不需要为「历史态」写第二套分支。

前端只需要两个入口：历史面板的「继续迭代」和首屏的会话恢复。会话恢复用 `localStorage` 只存 runId，内容仍从服务端读——直接把正文塞进 localStorage 会让 5 批快照撞上 5MB 配额。

## 我的确认与决策过程

| 决策点 | 选择 | 理由 |
|---|---|---|
| 历史续跑的产出归属 | 覆盖原批次（原地 rehydrate 同一 runId / batchId） | 高频动作是「隔天打开、微调一句、再发一次」，用户关心更新后的内容，不是并排对比；克隆会快速吃掉 5 个批次名额 |
| 刷新时已结束的任务 | 只提示，不抢屏 | 每次打开都被旧任务顶掉当前界面会很烦；运行中的才自动接回 |
| 会话过期时间 | 24 小时 | 超过一天的任务基本不会再接着改，留着只会干扰 |
| 批量模式恢复 | 只恢复已创建的任务 | 刷新发生在队列中间时，未启动的任务补不出来，硬造 pending tab 会永远待跑 |

## 实现

**回灌（`lib/orchestrator.ts`）**

```ts
export function resumeRun(snapshot: RunSnapshot & { batchId?: string }): RunState
```

- 内存已有同 runId → 直接返回，接口幂等
- `nodes` 走 `structuredClone`，避免后续重跑改到磁盘快照对象
- `outline` 取 `activeOutlineVersionId` 指向的版本，版本链原样保留
- `status / report / summary / createdAt / finishedAt / batchId` 全部继承

**接口（`app/api/run/[runId]/resume/route.ts`）**

内存命中 → 直接返回快照；未命中 → `loadRunSnapshot` 读盘回灌；都没有 → 404。回灌不触发任何模型调用。

**前端（`app/page.tsx`）**

- 历史面板每个版本旁新增「继续迭代」（原本是 button 套 button，改成 div 容器）
- `applySnapshotToView(snap)`：载入正常视图（非回看态），`editBtn` 恢复，只有 `running` 才连 SSE
- `applySnapshotsToBatch(mode, items)`：批量恢复，只给仍在跑的那个任务接 SSE
- `saveSession` 在单次启动、批量每个 runId 拿到后各写一次 `cab-last-run`
- 首屏 effect：读 session → 逐个 `GET /api/run/[id]` → 有 running 就自动接回，否则挂一条「上次任务 … 继续查看 / 忽略」
- 点「继续查看」先 `POST /api/run/[id]/resume` 回灌，再接回视图

**文档**

`docs/architecture.md` 新增「续跑与会话恢复」章节，补接口表、刷新行为矩阵与边界；关键设计决策加第 12 条。

## 验证

`npx tsc --noEmit` 通过；`npm run lint` 只剩 4 条本轮之前就存在的问题（`background-scene.tsx` ref、三处 effect 内 setState），本轮未新增。

浏览器实测（真模型）：

1. 历史面板 → 某批次「继续迭代」→ 提示「已接回…」，5 张卡全部 `完成`，策划卡展开后「编辑提纲」可用，版本 chips 为 `v1 · 策划原始` / `v2 · 手动编辑 · 当前`，提纲 1443 字完整还原。
2. 在接回的任务里改 `xhs.angle` 提交 → 提示「已提交「v3 手动编辑」，重生成范围：小红书笔记」，仅小红书回到生成中，长文/脚本/配图保持完成。
3. 长文再次编辑提交后立刻 F5 → 页面自动恢复，提示「已接回刷新前的运行」，长文显示生成中，其余三路仍是完成态。
4. 运行结束后核对 `GET /api/run/[id]`：`status=completed`、`versions=4`、`active=v4`；`POST /api/run/[id]/resume` 连续两次均 200（幂等）；不存在的 runId 返回 404。
5. `GET /api/history` 仍为 4 个批次，说明续跑是原地更新，没有产生新批次。
6. 已结束任务刷新 → 只出现「上次任务 / 继续查看 / 忽略」提示条，点「继续查看」后提示条消失、选题回填、5 个节点载入、`编辑提纲` 可用。

## 反思

- 「只读回看」和「可编辑」之间其实只差一次回灌，但前一版把落盘数据当成了纯展示层，导致最需要的场景反而被锁死。以后设计持久化时应该先问一句：这份数据除了看，还要不要能接着操作。
- 会话恢复选择「已结束不抢屏」而不是全部自动接回，是因为自动接回会让每次打开都像被旧任务绑架；但这也意味着用户要自己点一下，属于有意的取舍，需要观察真实使用中是否多余。
- 仍未解决、留待下一轮：编辑态没有「改完会重跑哪几路」的实时提示，版本 chips 也区分不出多个「手动编辑」的差异；这两条直接影响用户点提交前的判断，优先级高于其他打磨项。
