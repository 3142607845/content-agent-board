# Round 18：左侧可折叠侧边栏

## 我的提问

页面一直只有一列纵向内容，任务一多就只能靠批量 tab 和「历史记录」弹层找。新增迭代需求：加一条左侧可折叠侧边栏，承载项目名、最近任务列表、功能菜单、API 连接状态。

## 我的确认与约束

原始需求五条：

1. 整体改为「左侧侧边栏 + 右侧主内容区」，支持收起/展开，收起只留图标；
2. 侧边栏内容：顶部项目名、任务列表（标题/标签/时间/状态）、功能菜单（新建、风格模板、设置）、底部 API 状态；
3. 边界：新建自动入列、切任务清撤销栈、选中高亮；
4. 样式与现有页面统一，不破坏 SSE、提纲编辑、撤销重做；
5. 只改 `app/page.tsx` 与 `docs/architecture.md`。

三处歧义当场确认：

1. 任务列表 = 当前会话任务 + 服务端最近 5 批历史（不是只看当前会话）；
2. 现有 run 没有平台字段，标签位用创作维度/模式代替，不加模型字段；
3. 「设置」不做空壳，落一个轻量弹层（侧边栏收起 / 重看引导 / 清空本地会话记录）。

## 实现

布局：`BackgroundScene` 之后包一层 `relative flex min-h-screen`，左侧 `<aside>`，右侧 `min-w-0 flex-1 flex-col` 包住原 header 与 main。header / main 内部一行未动，SSE、提纲编辑器、撤销栈因此零改动风险。

侧边栏：

- 展开 264px / 收起 68px，`transition-[width]`；收起后 CA 徽标即展开按钮，菜单只留单字图标，任务条目只留状态点；
- 任务列表新增 `SidebarTaskItem` 展示模型，由「当前 run / `tasks` / `historyBatches`」拼装。当前会话的 runId 若已落盘则从历史段剔除，避免重复；
- 当前会话条目点击走 `setActiveTaskIndex` + 恢复批量模式；历史条目点击复用 `openHistoryRun`，不新写加载逻辑；
- 两种切换都在入口第一行调 `clearOutlineHistory()`，与任务 tab 的既有规则对齐；
- 「新建流水线任务」清空结果与草稿、回到输入区顶部，运行中禁用并写明原因；不删历史、不删成品库；
- 底部 API 状态复用 `GET /api/history` 做 30s 探测，`visibilitychange` 回到前台时补测。

数据补充：`TaskResult` 加 `createdAt`；单次模式新增 `singleCreatedAt`，值来自 SSE 首个 snapshot 的 `snap.createdAt`，回看与刷新恢复时取快照字段。

## 验证

静态检查：`npx tsc --noEmit` 通过；`npm run lint` 仍为 4 条既有问题（`background-scene.tsx` 1 条 + `page.tsx` 3 条 `react-hooks/set-state-in-effect`），没有新增。

过程中 lint 暴露两个新问题并已修正：

1. `createdAt: singleCreatedAt ?? Date.now()` 在渲染期调用 `Date.now`，触发 `react-hooks/purity`；
2. `handleStartSingle` 里 `setSingleCreatedAt(Date.now())` 同样被判定为渲染期不纯调用。

修法一致：单次任务的时间不再在前端取，改为从服务端 snapshot 的 `createdAt` 读；未拿到快照前该字段为 0，界面直接不渲染时间。

浏览器实测：

1. 侧栏显示项目名与 9 条历史任务；点 CA 徽标收窄为图标条，再点恢复；PASS；
2. 点「新建流水线任务」回到空态，历史条目仍在；PASS；
3. 点历史任务，右侧加载结果并出现「历史回看」条，该条目高亮；PASS；
4. 输入新选题启动，侧栏顶部立即出现该任务、状态点转蓝，节点正常流式输出；中断后状态点转琥珀色，条目保留；PASS。

## 反思

1. **侧边栏只读状态，不新增数据通道**。任务列表看起来是「新功能」，实际没有任何新接口、新持久化、新同步逻辑，全部由已有 state 派生。这样不会出现「列表说完成了、主区还在跑」的两套事实，也省掉了一整类一致性 bug。
2. **平台字段的缺失要如实暴露**。需求写的是「平台标签」，但现有 run 确实没有平台概念。硬造一个字段会污染模型和接口，所以用创作维度/模式占位，并在文档里写明这是临时语义，等真实平台字段进来再替换。
3. **lint 的纯度规则在逼着数据回到源头**。前端自己 `Date.now()` 记录任务创建时间看起来最省事，但规则拦下来之后，从服务端 snapshot 取 `createdAt` 反而是更正确的做法——任务本来就是在服务端创建的，时间也该以服务端为准。
4. **折叠态不持久化是主动取舍**。要做到刷新保持就得在 effect 里读 localStorage 再 setState，正好踩中已有的 lint 规则。界面偏好不值得为它新增一条报错，刷新恢复展开可以接受，文档里写清原因，避免下轮被当成遗漏。

## 补充：历史入口去重

侧边栏上线后立刻暴露一个问题：右上角「历史记录」和它重复了。

对照下来不是完全重叠，而是「入口重复、核心动作重复、边缘能力各占一半」：

- 侧边栏是单 run 粒度、含未落盘任务；历史面板是批次粒度、只有已落盘数据；
- 两边点击都是只读回看，但「继续迭代」只在面板里，批次刷新也只在面板里。

用户确认选择「侧边栏作为唯一入口」，于是：

1. 删掉 header 的「历史记录」按钮与整块批次面板，`historyOpen` state 一并删除；
2. 侧边栏历史段改为按批次分组，组标题用选题名（批量批次为「N 个选题」）加时间；
3. 历史条目右侧补一个「迭代」小按钮，直接复用 `resumeHistoryRun`，不动加载逻辑；
4. 首屏与流水线结束后的 `loadHistory` 继续负责刷新，不再需要手动「刷新」按钮。

验证：tsc 通过、lint 仍为 4 条既有；浏览器实测确认 header 无历史按钮、列表按批次分组、点条目回看高亮、点「迭代」进入可编辑视图。

反思：**重复功能最贵的不是多一个按钮，而是两份不一致的语义**。侧边栏和面板都在说「历史任务」，但一个含本地会话、一个只有落盘数据，用户看到两个数量对不上时，会开始怀疑数据本身。合并时保留能力最全的那个位置（侧边栏），把另一个的能力搬过来，而不是各留一半。
