# Round 05 — 阶段 2：编排引擎与四路并行

## 我的提问（用户视角）

按阶段 2 方案开始。开工前我对三个设计点做了决策：

1. **配图 Agent 模型**：不同意用 Doubao-Seed-2.1-pro，实测它生成的图片和我的主题没有多大关系，提出改用 GLM-5.3-Flash。
2. **单节点中断接口**：同意复用 `stop` 接口，通过 `?nodeId=` 参数区分，不单开接口文件。
3. **commit 拆分**：同意按「4 个内容 Agent → 编排引擎 → 接口与看板」三个 commit 顺序开发、逐块验收。

## AI 的方案

- **Run 状态**：内存态，挂 `globalThis` 上的 Map，防 dev 热更新丢状态。含 5 个节点状态、每节点独立 AbortController、事件缓冲、订阅者集合。
- **接口形态**：`POST /api/run` 创建 run 立即返回 `runId`；`GET /api/stream/[runId]` SSE 先回 snapshot 再推增量；`POST /api/stop/[runId]` 全局或单节点中断；`POST /api/rerun/[nodeId]` 复用提纲重跑。
- **SSE 事件协议**：`snapshot` / `node:start` / `node:token` / `node:image` / `node:done` / `node:error` / `node:cancelled` / `run:done` / `run:failed`。策划自动重试时重发 `node:start` 并带 `attempt: 2`。
- **中断语义**：严格按架构定稿。abort 只切断 LLM 流、不清 `content`；已完成节点完全不动；未启动节点标 `cancelled`。

## 我的确认与决策过程

**关于配图模型**，AI 指出一个技术事实：GLM-5.3-Flash 是智谱的原生多模态**理解**模型，能读图但不能出图，且智谱不在火山方舟，接入会打破「一个网关一个 Key」的架构。我接受了这个判断，改为先诊断问题根因。

**诊断结果**：策划 Agent 给的 3 条配图描述都是切题的，问题出在**扩写阶段**——扩写模型主动挑了三条里最抽象的那条（两只手相触），并进一步美化成纯意象，最终提示词里「AI」「编程」「程序员」「办公室」全部丢失，只剩「代码」两个字。所以换任何出图模型都没用，输入的语义已经偏了。

**我的决策**：选择「强化扩写约束」，改 `ImageAgent` 的 System Prompt，不动模型、不动架构。

## 遇到的三个真实问题（详见 pitfalls.md）

1. **中断失效（记录 05）**：策划还没跑完时中断 xhs，xhs 被标 `cancelled`，但策划完成后编排器又把它拉起来跑完了，最终 `completed` 820 字符。原因是调度入口只检查了全局 `run.status === "aborted"`，没检查节点自身的 `status === "cancelled"`，局部取消信号被全局状态覆盖。
2. **配图跑偏（记录 04 关联）**：诊断定为扩写阶段丢信息，强化约束后提示词从「机械手与手相触」变为「深夜办公室，程序员侧脸被显示器冷蓝光映亮」，四个关键要素（程序员/屏幕/代码/场景）全部命中。
3. **文档落后于代码 7 处**：架构文档是写代码前定稿的，阶段 2 中发生需求变更（换 Seedream）、实现细化（事件协议拆分）、我自己的命名偏差（`longForm.ts` vs `longform.ts`），三件事都没有回头同步。已逐条修复。

## 验收结果（我自己跑 + AI 辅助验证）

| 验证项 | 结果 |
|---|---|
| 正常全流程 | 5 节点全 `completed`，约 52 秒 |
| 策划 JSON 语法校验 | 通过，非 JSON 自动重试 1 次 |
| 4 路并行 | 同时启动，互不阻塞 |
| 配图出图 | Seedream 返回真实图片并渲染到卡片 |
| 单节点中断 | xhs `cancelled`，其余 4 个正常 `completed` |
| 单节点重跑 | 复用已生成提纲，重跑 longform 成功（4796 字符），其他节点不动 |
| 全局中断（策划阶段） | 策划 `cancelled` 保留 75 字符，4 个后置全 `cancelled` |
| 全局中断（并行阶段） | planner 1199 字、script 1113 字保持不动；longform 保留 176 字、image 保留 88 字；run 变 `aborted` |
| 浏览器实测 | 5 卡片全「完成」，配图可见，长文/脚本/小红书内容非空 |

## 关于按钮交互的一次确认

实测中我提出「中断」和「重跑」两个按钮区别不清，感觉必须先中断才能重跑。确认后保持现状：中断是「停」，重跑是「重来」；运行中禁用重跑是为了避免两条流写入同一份 `content`；节点完成后重跑可直接点，无需先中断。
