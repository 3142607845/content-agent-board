# Round 13 — 阶段 10：提纲编辑体验收口

## 我的提问（用户视角）

承接上轮实测留下的两条，都发生在「点提交之前」：

1. 改提纲时看不到这次改动会影响哪几路，提交后才从提示里知道范围，判断成本全压在一次真实生成上。
2. 版本链里多个「手动编辑」长得一模一样，回退时只能靠时间猜哪一版改的是小红书。

另外上轮还留了一个直觉冲突：只改顶层 `topic` 提交会被拒绝，但界面上看不出任何原因，只感觉按钮点了没反应。

本轮范围：**编辑体验一次收口**——影响面预览 + 版本渠道标注 + 只改选题的明确提示。

## AI 的评审意见

三条问题共用一个根因：渠道 diff 只有服务端知道。前端要做预览就得把比对逻辑再写一遍，而两份实现只要有一处边界不同（比如把 `topic` 算进渠道、空数组与缺字段的判定不同），用户就会看到「预览说重跑小红书、实际跑了长文」，比不预览更糟。

所以先抽 `lib/outline-diff.ts`，把渠道表、取片段、逐渠道序列化比对搬成纯函数，服务端 `regenerateFromOutline` 改成调用它，前端只负责把返回值渲染成一句话。预览与执行读同一份结果，不存在漂移空间。

版本标注顺带解决：`OutlineVersion` 加可选 `affected`，提交时把实际重跑的渠道记进版本。旧快照没有该字段就不显示，不需要迁移数据。

## 我的确认与决策过程

| 决策点 | 选择 | 理由 |
|---|---|---|
| 本轮范围 | 三条一起收口 | 都集中在策划卡编辑区，分开做要反复改同一段 UI |
| 只改 `topic` 怎么处理 | 保持拒绝，但前后端都说清原因 | 选题不影响四个渠道的产出，静默保存会造出一个「什么都没发生」的版本；彻底隐藏 topic 又要改编辑器结构，收益不值 |
| 预览怎么算 | 前端复用服务端同一份 diff | 两套逻辑必然漂移，预览失真比没有预览更糟 |
| `affected` 存哪 | 版本对象上加可选字段 | 旧快照缺字段直接不渲染，零迁移；回退时仍能看出那一版原本动了哪些渠道 |
| chip 文案 | 短名（长文/脚本/小红书/配图）+ 悬停全名 | 四个全名会把 chips 行撑开，短名足够区分 |

## 实现

**共用 diff（`lib/outline-diff.ts`，新增）**

```ts
export const OUTLINE_CHANNELS: { key: string; nodeId: NodeId }[]
export function outlineSection(outline: unknown, key: string): unknown
export function diffOutlineChannels(prev: unknown, next: unknown): NodeId[]
```

`orchestrator.ts` 删除本地渠道表与取片段函数，改为从新模块导入；`affected` 直接由 `diffOutlineChannels(run.outline, outline)` 得出。

**只改选题的提示**

服务端按「序列化后是否完全相同」区分两种拒绝文案：完全相同 → 「提纲没有变化，无需重生成下游」；仅 topic 变 → 「只改了选题：选题变化不影响四个渠道，请修改至少一个渠道的内容」。

**版本渠道标注**

`OutlineVersion.affected?: NodeId[]`，新建手动版本时写入。策划原始版本与旧快照没有该字段，chip 上不显示渠道段。

**前端（`app/page.tsx`）**

- 新增 `draftAffected`，草稿解析成功后即时与当前生效版本比对
- 提交按钮禁用条件从「全文没变化」改成「没有任何渠道变化」，只改 topic 也会被拦住
- 三态提示：与当前版本一致 / 只改了选题 / 将重跑：xxx
- 版本 chip 追加渠道短名（`CHANNEL_SHORT`），`title` 补全渠道名与提交时间

**文档**

`docs/architecture.md` 提纲章节新增「提交前影响面预览」「版本 chips 区分改动渠道」两段，补模块职责行与关键决策第 13 条。

## 反思

- 影响面预览真正要解决的不是「多显示一行字」，而是让「预览」和「执行」不可能对不上。只要两侧各自算 diff，这个保证就不成立，所以先抽公共函数再做 UI，顺序不能反。
- 只改 topic 的处理选了「拒绝 + 说清楚」，本质是在保护「每次提交都对应一次真实的渠道变更」这条不变量。如果以后真的需要改选题而不重跑，应该单独做「重命名批次」，而不是让提纲提交接口兼职。
- `affected` 是事故现场信息而不是状态：它只回答「这一版当时动了什么」，不参与任何调度判断。以后读版本链的逻辑不应该依赖它。
