# Round 08 — 阶段 5：全链路执行日志与 SSE 快照收敛

## 我的提问（用户视角）

前端已经打磨得差不多了，这轮补后端工程能力，我提了两点：

1. **全链路执行日志追踪**：每个 Agent 节点记录耗时、token 消耗、重试次数；流水线跑完后自动生成一份本次执行报告。
2. **完善 SSE 事件规范和快照下发逻辑**：网络断开重连时下发当前全量快照，解决重连后状态丢失。

## AI 的评审意见（两点里一点半是对的）

- **功能 2 其实已经做了一半**。`subscribe` 第一行就在推 snapshot，重连拿全量内容这条链路本来就是通的。真正坏的地方在别处：
  - `run:done` 是纯广播，不写回状态。重连时只能拿到 `status` 和 `nodes`，拿不到 summary 和结束原因。
  - **批量模式会卡死**：前端 `connectTask` 的 Promise 只靠 `run:done` resolve。断线期间 run 结束，重连后服务端推的是 snapshot，Promise 永远不 resolve，整个队列停在原地。这是真实 bug，不是理论风险。
  - 没有心跳，长连接空闲会被代理切断；`es.onerror` 是空函数，用户只看到卡住。
- **功能 1 的 token 不是「没做」，是「拿到也丢了」**。[llm.ts](file:///e:/content-agent-board/lib/llm.ts) 里 `if (!Array.isArray(choices) || choices.length === 0) continue;` 排在解析 usage 之前，而服务端把 usage 放在收尾分片里。
- **重试次数这个字段目前永远是 0**：只有策划节点有重试，其余 4 个节点恒为 `attempt=1`。只记录不扩能力的话，这个维度就是摆设。

## 我的确认与决策过程

AI 给了四个需要拍板的点，我全部选推荐项：

| 决策点 | 选择 | 理由 |
|---|---|---|
| token 口径 | 真实 usage + 自动降级 | 先实测能不能拿到，拿不到按字符估算并标注 `estimated`，不伪装精确 |
| 重试范围 | 4 个节点也加自动重试 1 次 | 否则重试字段恒为 0，这个维度没意义；顺带提升鲁棒性 |
| 报告出口 | 前端报告卡 + GET API | 演示时可以直接展示接口，也能脱离 SSE 调试 |
| 批量报告 | 每任务独立报告 + 汇总卡 | 多版模式能直接看出三个维度的成本差异 |

动手前先做了一件事：**实测方舟到底给不给 usage**。这一步省掉了后面所有返工。

## 实现要点

- **先验证再写码**：用一次 curl 打方舟，请求体带 `stream_options: { include_usage: true }`。结果比预期好——不仅返回了，还发现两个必须处理的细节：
  - 中间每个分片都带 `"usage": null`，不能直接赋值，必须判空。
  - `completion_tokens` **包含 reasoning_tokens**。实测一次 16 token 的输出全是思维链，正文是空的。所以报告里必须单独列 `reasoningTokens`，否则「输出 2000 token 但正文 800 字」会被当成算错。
- **改返回值还是加回调**：选择加 `onUsage` 回调，不动 `BaseAgent.run` 的返回值。理由是这个契约是「返回完整文本」，usage 属于调用元信息；如果改成 `{ text, usage }`，配图节点这种没有 usage 的就要造空对象，差异性会传染到类型层。
- **指标结构**：`AgentNodeState.metrics` 嵌套，含 `startedAt` / `endedAt` / `durationMs` / `usage` / `usageEstimated` / `retries`。重试时 `startedAt` 不覆盖，`usage` 累加——这样策划重试两次的耗时和成本都能算对。
- **终态写回**：`finishRun` / `failRun` 统一写 `status` / `finishedAt` / `summary` / `report`，再广播。报告必须落在 `RunState` 上，否则断线期间结束的 run 重连后什么都拿不到。
- **快照收敛而不是事件重放**：明确不做 `Last-Event-ID` 回放。全量快照已经能收敛全部状态，再维护事件日志表是过度设计。事件加自增 `id` 只为排查时序。
- **心跳**：每 15s 推一行 SSE 注释 `: ping`，不产生业务事件。`close()` 和 `req.signal` 两处都清理定时器。
- **重试下沉**：`isRetryable` 只放行网络异常、408、429、5xx；`AbortError` 和其余 4xx 不重试，避免用户点中断后又被重试拉起来。
- **并行加速比**：`serialMs` 是 4 个后置节点耗时之和，`wallMs` 是并行阶段实际墙钟时间，比值作为架构价值的量化指标。

## 遇到的问题

1. **TS 控制流把中断判断收窄没了**：`runTextNode` 开头判过一次 `run.status === "aborted"` 就 return，循环里再判同样的表达式，TS 认为不可能成立，直接报错。运行时中断确实可能发生在任意 `await` 之间。解决办法是抽一个 `isAborted(run)` 函数，函数返回值不参与调用方的控制流收窄。
2. **配图节点是并行阶段的瓶颈**：实测配图 105s，其余三个几十秒。加速比只有 1.58×，原因不是并行没生效，而是 4 路里有一路特别慢。这个数字是真实的，报告里照实给，不做美化。
3. **图片重试会产生孤儿文件**：重试时上一张图已经落盘到 `public/generated/`，但只有成功那次才推给前端。影响很小，本轮不处理。

## 验收结果

- `npx tsc --noEmit` 通过。
- **功能 1**：单次流水线实测 1m41s，报告卡渲染正常，表头含「输入 token / 输出 token」，每张 Agent 卡片显示耗时与 token 角标（如 `13.0s` / `473` / `759`），token 全部是服务端真实值，未走估算路径。
- **功能 2** 三项都做了接口级验证：
  - 连接到**已结束**的 run：snapshot 立即返回 `status: completed`，带 `summary` 与 `report`。
  - **运行中断线**后重连：snapshot 带回策划已累积的 617 字，状态没丢。
  - 心跳：连接 17s 后收到 `: ping` 注释行。
- 浏览器控制台无 error。

## 反思

上一轮的教训是「做差异化功能时先问差异体现在哪个字段上」。这一轮的教训更基础：**用户报的现象和真正的缺陷经常不在一处**。需求写的是「重连后状态丢失」，但快照机制本来就在，真正的坑是批量队列会卡死、以及终态从来没被存下来。如果照着字面去「实现快照下发」，会做出一堆重复代码，而 bug 还在。

另一个收获是「先花一分钟验证外部接口，再决定方案」。token 这件事只差一个 curl，但如果不先测，很可能写完一整套解析逻辑才发现字段拿不到，然后被迫改成估算，报告的可信度就没了。
