# Round 19：内测视角盘点与四批体验收口

## 我的提问

功能层面已经跑通，要求切换到真实内测用户视角（常做小红书、公众号、短视频脚本的自媒体创作者），把左侧任务侧边栏、流水线多 Agent 生成、差异化提纲、提纲编辑撤销重做、风格模板库、SSE 流式推送、历史任务回看全用一遍，找出别扭、反直觉、麻烦、容易误操作的地方。输出要包含痛点场景、对创作的麻烦、贴合现有架构的优化方案、优先级分级，最后汇总成可直接开发的迭代清单，并注明每项是否影响 SSE、撤销栈、侧边栏切换逻辑。

## 我的确认与约束

1. 不推翻已有功能，只补体验卡点，不加炫酷新功能；
2. 方案要贴合现有架构：状态存 `globalThis` Map、SSE 快照收敛、历史按 `batchId` 落盘、提纲编辑走本地撤销栈；
3. 产出按「高（严重影响使用）/ 中（明显不顺手）/ 低（锦上添花）」分档，并分成三批开发。

盘点结果 15 条：高 4 条、中 7 条、低 4 条。实际落地时按四批提交，其中 hero 折叠一项被用户当场否决并回退。

## 实现

### 第一批：草稿守护与运行中护栏

- **切任务丢草稿**：提纲编辑态下直接点侧边栏任务、控制台任务 tab、横向对比表头或对比单元格，草稿会无声消失。新增 `outlineBaselineRef` 记录进入编辑时的原始提纲，`beginTaskSwitch()` 用「草稿是否偏离基线」判断脏值，脏则 `window.confirm` 拦截，干净则直接放行。四条入口统一走这一个函数。
- **运行中点历史**：回看会关闭当前 SSE，而批量队列的下一个 run 只有收到终态才继续，中途 close 会让整条队列永久卡住。新增 `hasLiveRun`（单次看 `isRunning`，批量看整批 `running / pending / queued`），运行中点历史只提示「流水线运行中，结束后再回看历史任务」，同时把「迭代」按钮置灰。

### 第二批：手感与文案

- **撤销记录点**：原来只在失焦时记一步，连续输入后一次撤销丢掉一大段。改为输入停顿 1.2s 自动记一步（`OUTLINE_AUTOSAVE_MS`），失焦兜底，上限仍为 20 步；按钮旁显示「可撤销 N 步」，让撤销栈不再是隐形的。
- **回看横幅主按钮**：历史回看横幅增加「继续迭代」主按钮，不再要求用户先找到侧边栏小图标。
- **本批对比入口**：批量任务完成后，回看态直接提供「本批对比」，不必再回主视图找入口。
- **复制全部**：每张内容卡增加「复制全部」，一次拿到完整产出，省掉整段选中。
- **服务状态文案**：底部探测文案从「API 已连接」改为「本地服务正常 / 未响应」，因为这条探测只打 `/api/history`，不代表模型接口可用。
- **收起态任务列表**：侧边栏收起后任务条目只留状态点，补 title 提示，鼠标悬停可辨认。
- **设置项澄清**：「清除刷新恢复记录」补写只影响刷新后自动接回，不删历史与成品库。

### 第三批：提纲结构化表单

提纲原来只能手改 JSON，对非技术用户门槛过高。新增表单/JSON 双模式：

- `OutlineDoc` 识别成功时渲染四渠道表单块（长文段落要点、短视频分镜、小红书标题与标签、配图描述词），字段数组按「每行一条」编辑；
- 结构无法识别时自动落回 JSON 模式并提示，不阻塞原有用法；
- 所有表单改动统一经 `updateOutline()` 序列化回 `outlineDraft`，撤销栈、影响面预览、提交接口读的仍是同一份草稿，没有新增数据通路。

同批做了风格模板入口去重（header 与侧边栏各一个入口），用户否决删除 header 入口并要求恢复全部功能，最终定为「两处入口指向同一个三栏面板」。

### 第四批：历史删除、排队状态与队列拦截

- **历史批次删除**：新增 `deleteHistoryBatch(batchId)` 与 `DELETE /api/history?batchId=`，侧边栏历史组头加删除按钮，删除前二次确认并写明成品库收藏不受影响；回看中的批次被删时自动退出回看。历史段底部补「本地保留最近 5 批，重要产出请收藏到成品库」的容量提示，把静默淘汰变成可见规则。
- **排队状态**：批量选题创建后先置 `queued`，轮到才转 `running`；任务 tab 显示灰点加「排队」小字，侧边栏显示「排队中」，进度行追加「排队 N」。此前排队中的任务看起来和已完成无异。
- **队列中拦截新建**：「新建任务」与模式切换的守卫从 `isRunning` 改为 `hasLiveRun`，覆盖排队项，避免队列还在推进时把界面切走。

### 被否决项：hero 折叠

曾实现首屏说明区在有任务后折叠为一行。用户实测后明确否决：「这个界面我要默认是展开的，我觉得这样更美观不要你原来的那个收起方案」。已完整删除 `heroOpen`、`heroFull` 与收起/展开按钮，恢复始终完整展示，文档同步改为「首屏说明区始终完整展示」。

### 收尾：lint 归零

四轮功能做完后统一收口静态检查：

- `background-scene.tsx` 的 `activeRef.current = active` 从渲染期赋值改为 effect 内同步，属于真问题，正经修掉；
- `page.tsx` 三处挂载期副作用（拉历史/成品库/项目库、拉风格模板、读 `localStorage` 决定是否弹引导）加精准 `eslint-disable-next-line` 并写明原因：前两处 setState 都在 `await` 之后，规则看不到 await 边界；引导一项只有浏览器能判断，惰性初始化会造成 hydration 不一致。

## 验证

1. `npx tsc --noEmit` 通过；`npm run lint` 从 4 条既有报错收敛到 0；`npm run build` 生产构建成功，16 条路由正常产出。
2. 浏览器实测：提纲编辑后点侧边栏另一任务弹出确认框；批量任务运行中点历史只出提示；停顿输入后撤销按钮显示步数并可回退；提纲表单四渠道可编辑且与 JSON 双向一致；历史组头删除后列表与容量提示同步更新；新建的排队任务在 tab 与侧边栏均显示排队中，此时新建按钮置灰。
3. 说明：排队状态只在队列内生效，SSE 事件协议未改动；撤销栈与影响面预览仍读同一份草稿；侧边栏仍是纯派生视图，未新增接口。

## 反思

1. **草稿守护要比「是否编辑过」，不是「是否打开过」**。刚点进编辑就切任务不应该打扰用户，基线对比让确认框只在真正有改动时出现。
2. **运行中判定必须覆盖整批**。只看当前 run 的 `isRunning` 会漏掉排队中的队列，而队列恰恰是最怕被打断的场景。
3. **结构化表单不新建数据通路**。表单看起来是一套新界面，实际只是 `outlineDraft` 的另一种呈现，序列化后回写同一份 JSON，撤销栈和提交链路零改动。
4. **双入口原则要按功能区分**。「一个功能只留一个入口」对导航类成立（历史记录合并进侧边栏），对工具类不成立（风格模板两处入口指向同一面板，用户更在意顺手）。
5. **界面偏好不要用折叠换空间**。hero 折叠看起来能省一屏，但用户判断「默认展开更好看」，说明省一次滚动不如信息完整。这类偏好类改动立项前应先确认。
6. **静默规则要写出来**。历史只留 5 批是既有实现，但界面从不说明，用户会以为数据丢了。容量提示比优化淘汰策略更有效。
