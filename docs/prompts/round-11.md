# Round 11 — 阶段 8：提纲人工干预与版本回退

## 我的提问（用户视角）

深度使用后发现的真实问题：Planner 生成 3 版提纲之后，提纲是只读的，我没法改。只要对某一版提纲不满意，就只能重新发起整条流水线，策划和 4 个下游 Agent 全部重跑，token 和时间都浪费。

所以规划新增：**提纲人工干预、回退重生成指定版本**。

1. 前端提纲卡片支持直接编辑修改；
2. 编辑完成后提供【基于当前提纲重生成下游】，只调用提纲之后的下游 Agent，不再重新执行 Planner；
3. 保存本次流水线内所有提纲版本记录，支持回退任意历史版本并基于其重生成下游；
4. 未改动的模块产出内容保留，仅更新受提纲影响的内容。

适用场景是自媒体创作者微调大纲、局部更新文案脚本，不需要全量重跑。

## AI 的评审意见

需求成立，且不需要改流水线拓扑：`run.outline` 本来就是下游的唯一输入，`rerunNode` 也已经证明「复用提纲、不重跑策划」可行。真正要补的是三件事——提纲的版本模型、下游的 diff 粒度、编辑态与运行态的互斥。

提出三个必须先定下来的取舍：

1. 提纲怎么编辑？结构化表单逐字段改体验好，但四渠道字段各异，且以后新增字段就要改表单；整段 JSON 编辑能覆盖全部字段、回退可逐字节还原，代价是需要前端做语法校验。
2. 「重生成下游」到底跑几个？全部 4 个最直观，但会覆盖用户已经满意、根本没改的渠道产出，与需求 4 冲突。
3. 回退是否要新增版本？如果每次回退都追加一份内容相同的版本，版本链很快会被刷爆。

## 我的确认与决策过程

| 决策点 | 选择 | 理由 |
|---|---|---|
| 编辑形态 | 整段 JSON 编辑 + 实时语法校验 | 覆盖策划输出的全部字段，回退能精确还原；非法 JSON 禁止提交 |
| 重生成范围 | 仅重跑提纲有变化的渠道 | 直接满足「未改动模块产出保留」，也最省 token |
| 版本保存 | 每次提交自动追加；与历史版本一致时复用 | 回退不产生重复版本，版本链始终可读 |

## 实现

**数据层（`lib/orchestrator.ts`）**

- 新增 `OutlineVersion { id, label, source, createdAt, outline }`；`RunState` 增加 `outlineVersions` 与 `activeOutlineVersionId`，随 `RunSnapshot` 下发并落盘。
- `runPlanner` 解析成功后写入 `v1 策划原始`，作为版本链起点。
- 新增 `regenerateFromOutline(runId, outline)`：校验状态与结构 → 按 `longForm/script/xhs/image` 逐渠道 diff → 复用或追加版本 → 只 reset 受影响节点 → 重新调度并在结束后重新生成报告。
- `runParallel` 拆成 `runDownstream(run, nodeIds)`：正常流水线传 4 个节点，重生成只传 diff 出来的渠道。

**接口**

`POST /api/outline/[runId]`，请求体 `{ outline }`。错误码：run 不存在 404、有节点在跑 409、策划未完成/结构非法/内容无变化 400。成功返回 `{ version, versions, affected }`。

**前端（`app/page.tsx`）**

- 策划卡展开态新增「编辑提纲」入口，textarea 内是格式化后的当前版本 JSON，实时提示语法错误。
- 编辑区上方渲染版本 chips（`v1 · 策划原始 · 当前`、`v2 · 手动编辑`），点任意版本即载入编辑器，实现回退预览。
- 主按钮「基于当前提纲重生成下游」，与当前版本一致时禁用；提交成功后重连 SSE，卡片按局部重跑状态刷新。
- 策划 `node:done` 时补拉一次快照，让版本链在运行中就可用；历史回看态只读，不显示编辑入口。

接口层共 26 条断言全部通过；测试产生的 run 快照已清理。

## 反思

- 需求写的是「只调用提纲之后的下游 Agent」，但用户真正想要的是「别把我已经满意的产出冲掉」。如果照字面全部重跑，功能能用，体验却会退步——所以按渠道 diff 是必要的一步，而不是过度设计。
- 版本复用（内容相同就激活旧版本）是个很小的判断，但它决定了回退功能长期是否可读。没有它，来回切两次就会多出四份内容相同的版本。
- 编辑能力必须和运行态互斥。文本可以随时改，但提交必须等当前节点结束，否则同一个节点会被两个 `runTextNode` 同时写，状态会直接错乱。
- 这轮几乎没有改流水线本身：版本链是包在 `run.outline` 外面的一层，`runDownstream` 只是把「跑哪几个」变成参数。好的迭代应该让新功能贴着旧结构长出来，而不是把旧结构推倒重来。
